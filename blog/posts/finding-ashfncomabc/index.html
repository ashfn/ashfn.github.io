Finding ashfncomabc: an RTX 3070 Tor vanity-address experiment

2026-09-14

I wanted to make a Tor version of this site. Running an onion service myself seemed like a good way to understand how it worked.

An onion service is reached entirely through the Tor network. The connection is encrypted between the visitor and the service, and the protocol lets a service accept connections without publishing its server’s IP address. The Tor Project’s explanation goes through how the two sides find each other.

Before I got very far with the hosting, though, I got distracted by the address.

Why a vanity address?

A normal Tor v3 address is a string of 56 base32 characters followed by .onion. Unlike a regular domain, it comes from a cryptographic public key. You cannot just register ashfncom.onion and point it at a server.

I wanted something I could recognise in a list of otherwise random-looking addresses. A prefix like ashfncom makes the connection to this site obvious at a glance, and makes the address easier to distinguish when sharing or bookmarking it. It does not shorten the rest of the address, and checking a familiar prefix is not the same as verifying the full hostname, but it is a useful visual cue.

To get that prefix, you have to search: generate candidates, check their public keys, and keep a key whose address begins with the letters you want. Longer prefixes quickly turn that search into a substantial computation. That was the part that caught my attention.

Why try a GPU?

There were already tools for this. cathugger’s mkp224o could generate the address I wanted, and simply running it on the CPU would have been a perfectly reasonable way to finish the hosting project.

But I had an RTX 3070, and I wanted to see whether I could make the search faster by using it. Cryptocurrency mining was the example I had in mind: early GPU miners had shown how effective lots of parallel workers could be at repetitive cryptographic calculations. That made a search with many independent candidates seem like a promising GPU workload.

Mining’s hash calculations are different from the elliptic-curve arithmetic here, so I still needed to find out how well this particular search would run on a GPU. I decided to build a CUDA version and benchmark it against mkp224o.

Starting with the CPU

For the CPU baseline, I ran mkp224o on a Ryzen 7 2700X with eight cores and sixteen hardware threads. The same machine had the RTX 3070 with 8 GiB of VRAM. The GPU stayed at its default 220 W power cap; I did not change its clocks, power limit or fan settings.

I tried several mkp224o arithmetic backends and thread counts. The fastest configuration used amd64-64-24k, sixteen threads, integer filtering and upstream batch mode, compiled with -O3 -march=native -fomit-frame-pointer.

Three separate 30-second CPU runs gave a median of 42.029 million candidates/sec, with results between 42.004 and 42.273 million. I used the long filter zzzzzzzzzzzz so successful key exports would not keep interrupting the benchmark. The last cumulative CPU samples were at about 29.1 seconds, because shutdown did not emit another sample.

Building it with Astra

I had never written CUDA kernels before, so I used OpenAI’s new GPT-6 Astra to help write and iterate on them. It also helped with the Python/CuPy runner and the checks needed to compare successive versions.

Python handled initialization, compilation, launches and saving matches, while the CUDA kernels did the expensive arithmetic on the GPU. CuPy compiled those kernels through NVRTC, so the setup did not need a system installation of nvcc.

The arithmetic itself came from an existing implementation: the source generator adapts ref10 from the pinned mkp224o source into CUDA device functions. The main job was arranging that arithmetic into an efficient search.

What is a candidate?

A Tor v3 hostname encodes a 32-byte Ed25519 public key, a two-byte checksum and a version byte into 56 base32 characters. For a short vanity prefix, the search can check the relevant public-key bits directly.

Each GPU lane starts from its own OS-random seed. The CPU expands and clamps the secret and initializes the public points. If the initial secret scalar is a0a_0a0​ and the Ed25519 base point is BBB, the lane walks through:

ai=a0+8i,Pi=aiB.a_i = a_0 + 8i, \qquad P_i = a_i B.ai​=a0​+8i,Pi​=ai​B.

That means the next public point is simply:

Pi+1=Pi+8B.P_{i+1} = P_i + 8B.Pi+1​=Pi​+8B.

Adding a fixed point is much cheaper than doing a complete scalar multiplication for every candidate. Secret material stays on the CPU; the GPU receives public points. When it reports a hit, the CPU reconstructs the full public key independently with libsodium, verifies it and generates the complete onion hostname.

Throughout this post, throughput means candidate public-key prefix checks.

Montgomery’s trick

One expensive part of checking a candidate is converting projective coordinates back into an affine coordinate. In the original Edwards kernel, recovering yyy involves:

y=Y/Z=YZ−1(modp),p=2255−19.\begin{aligned} y &= Y/Z = YZ^{-1} \pmod p,\\ p &= 2^{255}-19. \end{aligned}yp​=Y/Z=YZ−1(modp),=2255−19.​

A field inversion is much more expensive than a multiplication. Doing one inversion for every candidate wastes a lot of work.

Montgomery’s trick computes the inverses of a whole batch using just one inversion. Suppose the batch has nonzero denominators z1,…,znz_1,\ldots,z_nz1​,…,zn​ in Fp\mathbb{F}_pFp​. First calculate their prefix products:

P0=1,Pi=∏j=1izj.P_0=1, \qquad P_i=\prod_{j=1}^{i}z_j.P0​=1,Pi​=j=1∏i​zj​.

Then invert only the final product:

r=Pn−1.r=P_n^{-1}.r=Pn−1​.

Work backwards through the batch. At each step:

zi−1=rPi−1,r←rzi.\begin{aligned} z_i^{-1} &= rP_{i-1},\\ r &\leftarrow rz_i. \end{aligned}zi−1​r​=rPi−1​,←rzi​.​

Why does this work? Before processing index iii, we have r=Pi−1r=P_i^{-1}r=Pi−1​. Since Pi=Pi−1ziP_i=P_{i-1}z_iPi​=Pi−1​zi​:

Pi−1Pi−1=zi−1.P_i^{-1}P_{i-1}=z_i^{-1}.Pi−1​Pi−1​=zi−1​.

Multiplying the running inverse by ziz_izi​ then leaves Pi−1−1P_{i-1}^{-1}Pi−1−1​, ready for the next step.

For three denominators, it looks like this:

r=(z1z2z3)−1,z3−1=r(z1z2),r←rz3=(z1z2)−1,z2−1=rz1,r←rz2=z1−1.\begin{aligned} r &= (z_1z_2z_3)^{-1},\\ z_3^{-1} &= r(z_1z_2),\\ r &\leftarrow rz_3=(z_1z_2)^{-1},\\ z_2^{-1} &= rz_1,\\ r &\leftarrow rz_2=z_1^{-1}. \end{aligned}rz3−1​rz2−1​r​=(z1​z2​z3​)−1,=r(z1​z2​),←rz3​=(z1​z2​)−1,=rz1​,←rz2​=z1−1​.​

Ignoring multiplications by one at the boundaries, the basic batch-inversion algorithm replaces nnn inversions with one inversion and 3(n−1)3(n-1)3(n−1) multiplications. Recovering coordinates adds its own multiplications. The nonzero-denominator assumption matters: zero has no field inverse.

On the GPU, each lane batches its own candidates. Larger batches spread that one expensive inversion across more work, but need more scratch memory. Finding a good batch size was a large part of the tuning.

Crossing a billion

The first sustained CUDA configuration used 32,768 lanes, 128 candidates per lane per batch, and 64 threads per block. It needed 0.625 GiB of scratch storage and reached a three-trial median of 896.748 million candidates/sec.

I then specialized compilation for the prefix length and diagnostic mode. The actual prefix letters stayed runtime inputs, but the compiler could remove irrelevant branches, unused encoded bytes and sign handling that short prefixes did not need. Compiler-reported register use fell from 242 to 180 registers per thread, with no local spill storage in those two compared variants.

Increasing the batch to 256 and using 32 threads per block pushed the median to 1.010 billion/sec. All three 30-second trials exceeded a billion, although throughput declined as the card warmed. Scratch storage increased to 1.25 GiB.

A cheaper curve walk

The next improvement came from studying ActiveTK’s GPUonion, particularly its optimization notes. The useful idea was a different coordinate representation and differential addition. This also carries Montgomery’s name, but is separate from the batch-inversion trick above. I applied the technique to the existing ref10 implementation; no GPUonion source files were copied or vendored.

The Edwards yyy coordinate and Montgomery coordinate uuu are related by:

u=1+y1−y,y=u−1u+1.u=\frac{1+y}{1-y}, \qquad y=\frac{u-1}{u+1}.u=1−y1+y​,y=u+1u−1​.

Writing u=U/Wu=U/Wu=U/W gives a convenient projective form:

y=U−WU+W.y=\frac{U-W}{U+W}.y=U+WU−W​.

These coordinate relationships are also described in RFC 7748. The kernel keeps the current and previous points, whose difference is the fixed step 8B8B8B. Let:

N=U−W,D=U+W,κ=y(8B).\begin{aligned} N &= U-W,\qquad D=U+W,\\ \kappa &= y(8B). \end{aligned}Nκ​=U−W,D=U+W,=y(8B).​

The next projective point can then be computed as:

Unext=Wprev(N+κD)2,Wnext=Uprev(N−κD)2.\begin{aligned} U_{\mathrm{next}} &= W_{\mathrm{prev}}(N+\kappa D)^2,\\ W_{\mathrm{next}} &= U_{\mathrm{prev}}(N-\kappa D)^2. \end{aligned}Unext​Wnext​​=Wprev​(N+κD)2,=Uprev​(N−κD)2.​

This is the recurrence used in my kernel: three field multiplications and two squarings per step, compared with seven multiplications in the previous Edwards mixed addition. Because the step is fixed, κ\kappaκ can be compiled into the kernel as a constant.

Combining it with batch inversion

We still need to recover each candidate’s Edwards yi=Ni/Diy_i=N_i/D_iyi​=Ni​/Di​ to check its prefix. Here the same batch-inversion idea also saves memory.

Let Qi−1Q_{i-1}Qi−1​ be the product of the preceding denominators. During the forward pass, store a weighted numerator:

Q0=1,Qi=Qi−1Di,Ai=NiQi−1.\begin{aligned} Q_0 &= 1,\\ Q_i &= Q_{i-1}D_i,\\ A_i &= N_iQ_{i-1}. \end{aligned}Q0​Qi​Ai​​=1,=Qi−1​Di​,=Ni​Qi−1​.​

Invert the final product once, then walk backwards. When the running inverse is r=Qi−1r=Q_i^{-1}r=Qi−1​:

yi=Air=NiQi−1Qi−1=NiDi−1,r←rDi.\begin{aligned} y_i &= A_i r\\ &= N_iQ_{i-1}Q_i^{-1}\\ &= N_iD_i^{-1},\\ r &\leftarrow rD_i. \end{aligned}yi​r​=Ai​r=Ni​Qi−1​Qi−1​=Ni​Di−1​,←rDi​.​

Now the scratch buffer only needs AiA_iAi​ and DiD_iDi​. There is no separate array for every prefix product. Normal scratch reads and writes dropped from 240 to 160 bytes per candidate. That allowed a batch of 512 in the same 1.25 GiB allocation.

The final configuration was 32,768 lanes × 512 candidates, with 32 threads per block: 16,777,216 candidates per launch.

There is a limitation: the Montgomery-only state loses the Edwards xxx sign. The automatic backend uses this path for prefix lengths 1–49, falling back to the Edwards kernel for lengths 50–51.

The final three GPU trials measured 1.347, 1.338 and 1.330 billion/sec, each over about 30 seconds. That is a 32.50% improvement over the specialized Edwards median.

These GPU timings include launches, synchronization, result-counter reads and hit-index transfers. They exclude initial seed generation, context setup, JIT compilation, warm-up and writing key files. Short tuning sweeps helped choose settings, but the headline figures come from the repeated trials.

During a longer search, a recorded window of about 27 minutes averaged 1.311 billion candidates/sec, including initialization and pauses to save matches and reseed. That average comes from total completed candidates divided by total measured time. The full campaign checked 2,615,299,538,944 candidates.

The lucky part

The campaign retained four ashfncom addresses. One of them was much nicer than I had expected:

ashfncomabccvkuuvzbsjobu5wvtlw2wpz4mj3co5g5boyturbf36cyd.onion

I had only asked for ashfncom; the extra abc appeared by chance.

Found on 14 September, UTCAddress beginning
08:17:33.685473ashfncomfeay…
08:36:08.983447ashfncomabc…
08:36:11.810204ashfncomkvt4…
08:43:31.083073ashfncomtbcj…

The second and third matches were only 2.827 seconds apart, after a much longer preceding gap. Random searches do not produce evenly spaced successes.

Under the usual uniform-prefix model, an eight-character base32 target has probability:

Pr⁡(match)=32−8.\Pr(\text{match})=32^{-8}.Pr(match)=32−8.

At the final benchmark median, the expected waiting time is:

E[T]=328R≈13.70 minutes.\mathbb E[T]=\frac{32^8}{R} \approx 13.70\text{ minutes}.E[T]=R328​≈13.70 minutes.

Every extra specified character multiplies the expected work by 32. Deliberately searching for all eleven characters of ashfncomabc would take about 312 days on average at the same uninterrupted rate:

E[T11]=3211R.\mathbb E[T_{11}]=\frac{32^{11}}{R}.E[T11​]=R3211​.

Given an ashfncom match, a particular three-character extension such as abc has probability 32−332^{-3}32−3, or one in 32,768. Across four matches, the probability of at least one pre-specified abc extension is:

1−(1−32−3)4≈0.0122%.1-(1-32^{-3})^4\approx 0.0122\%.1−(1−32−3)4≈0.0122%.

But I noticed the nice extension after seeing the results. Other memorable endings might also have made me happy. This was an eight-character search that got lucky, not evidence that an intentional eleven-character search normally takes minutes.

Checking and keeping the keys

Speed is only useful if a saved key controls the hostname it claims to. The checks compared GPU results with libsodium, exercised long walks and scalar carries, tested prefix masks and batch boundaries, and verified Tor’s file formats and hostname checksums. The Montgomery suite covered 104,007 candidate checks, including 69,338 serialized yyy-coordinate comparisons. Those are test counts, not a claim of that many independent secret keys or a cryptographic audit.

The continuous runner validated each match before saving it, wrote through a temporary directory, flushed the files and atomically moved the finished result into place. Key files had mode 0600, and directories 0700. There were no incomplete exports.

It also exported at most one match from a walker’s lifetime, then initialized all lanes again with fresh randomness. Keeping multiple keys from related scalar walks would expose a known relationship between their secrets. The reseeding cost is included in the longer-run average above.

Putting the site on Tor

With the address found, I could finally get back to the original idea. After a small Hello World test, I put Tor and Nginx in a simple Alpine-based Docker container to serve this site through the onion address.

The site itself is built with Eleventy: posts are Markdown or MDX files, projects live in one JSON file, and the build produces static HTML and assets. For local testing, Nginx forwards requests from the container to the server on port 4000. Editing a post rebuilds the same files that both the normal preview and onion site serve.

The important part of the Tor configuration is:

HiddenServiceDir /var/lib/tor/site
HiddenServiceVersion 3
HiddenServicePort 80 127.0.0.1:8080

The directory holds the saved vanity identity, and the last line forwards the onion service’s port 80 to Nginx inside the container. Nginx then proxies to host.docker.internal:4000. This follows the basic arrangement in the Tor Project’s setup guide.

The original key directory is mounted read-only and copied into a persistent Docker volume on first start, so rebuilding the container keeps the same address. The keys stay out of the image and repository. No container ports need to be published, and the proxy blocks the local editor at /editor/.

With the local server running and the key directory configured, starting it is just:

docker compose -f tor/compose.yaml up -d --build

A separate Tor client successfully fetched the homepage and this article, with responses matching the local site. This setup depends on my machine, Docker and the local server staying on; it is still a local mirror.

Making it work without JavaScript

I also wanted someone opening the onion address to be able to read and use the site with scripts turned off. Tor Browser’s Safest setting disables JavaScript by default and restricts some fonts, icons and images, so testing with JavaScript disabled alone was not enough.

I kept the layout from the old Next.js site but moved the rendering to build time. Articles, syntax highlighting and these equations arrive as ready-made HTML and CSS. The browser does not need React to display them.

For the controls, I used what the browser already provides. The contents list uses anchor links, expandable JSON uses details and summary, and the theme button is a checkbox whose state changes the colours through CSS. Code can be opened as plain text for manual copying. Small optional scripts add conveniences such as remembering the theme, copying to the clipboard and following the current heading while scrolling; the Easter eggs also need JavaScript.

The icons caught me out: some SVGs disappeared in the stricter browser settings, leaving empty buttons and link boxes. I replaced the small UI icons with a single PNG sprite, using CSS masks to colour them for either theme. I then checked the pages in Firefox with JavaScript, SVG rendering and downloadable fonts disabled, at desktop and mobile sizes.

I set out to put this site on Tor and ended up spending most of the time on its address. The unexpected abc made that detour especially satisfying, but having a small site that still works with scripts turned off felt like a good way to finish it.
